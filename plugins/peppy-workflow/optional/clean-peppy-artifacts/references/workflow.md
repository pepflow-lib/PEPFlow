# Prepare a complete Peppy distribution

## 1. Fix the source and delivery boundary

Identify the completed examples and the exact directory to clean or populate. Inspect Git status, ongoing work, the existing output layout and active core workflows, and publication/run instructions. Read the manuscript when available; if unavailable, report that limitation and retain uncertain publication artifacts. Do not claim a paper-reference audit without reading it. A cleanup request does not authorize editing another repository, sweeping sibling examples, or treating a paused analysis as completed.

Establish the protected delivery contract before identifying removals: each main setup module, all completed B1-B5 states, required dense/relaxed results, certificates, basis/rank/dual evidence, closed-form handoffs, existing workflow/publication deliverables, and their transitive dependencies. Preserve existing `state/` and `supplementary/` roots with their meaningful content. These roles remain protected when the notebook inlines or regenerates their contents or never reads them during Run All. Cleanup authorization covers disposable debris and the narrow edits in Sections 2-3, not dropping this contract.

For a selected completed example or delivery tree, cleanup within that retention contract is allowed in place. For an original evaluation campaign or frozen source archive, require a distinct delivery destination and copy only the selected retained set there; keep the original campaign, submissions, outcomes, and time/token records unchanged. Do not infer that a frozen archive is disposable because a notebook can execute without its records. If source and delivery roles remain ambiguous, resolve that boundary before mutation.

The core five-block workflow stays at the version already selected for the project. This skill neither upgrades it nor chooses an older experimental version. Record baseline hashes of selected notebooks, retained sources, and active workflow instructions internally for change review and concurrent-edit detection. These are cleanup bookkeeping, not new notebook execution requirements or distribution files. Preserve unrelated user changes.

## 2. Remove historical source authentication

Inspect notebook cells, helpers, and executed serialized code for requirements that source bytes match an earlier run. This applies to framework, setup, example, and proof source, including archived source strings. Classify each check by its role: historical source identity is distinct from certificate-payload integrity and mathematical verification. A hash name or failing assertion alone does not identify a removal target.

Remove historical source-byte comparisons, failure gates, authentication reports, and source archives used only for those checks. Remove their obsolete explanatory text and initialization. Where an authentication helper also resolves paths or executes saved code, preserve those necessary operations using current distributed paths and minimal edits to existing notebook cells or replay sources, then remove the unused helper only if it has no protected artifact role or remaining consumer. Do not create replacement compatibility modules, current-source pins, historical copies, archives, or hash reports. Do not report skipped checks as verified or replace verifiers with unconditional success.

Preserve certificate payloads, IDs, mathematical data, and current data-integrity checks, except for the verified delivery-path metadata migration in Section 3. Historical `certificate_provenance` and `source_hashes` fields may contribute to a certificate ID: leave that historical metadata inert rather than erasing it or recomputing IDs merely to remove source authentication. Metadata alone does not require authentication-only source archives to remain; it does not make a setup module, workflow state, or numerical certificate/data archive disposable. Operational replay-source fields outside the certificate payload may be edited to remove historical authentication and use current paths; preserve their mathematical operations. If removing source authentication would change protected certificate data, retain the affected dependency and report the concrete limitation. The Section 3 exception permits only a verified delivery-path metadata migration, not changes to numerical or proof data.

Keep setup/parameter/coordinate/constraint reconstruction and every existing residual, sign, PSD, domain, base, boundary, and symbolic identity check, with the same conditions and tolerances. Keep visible proof code and execute the actual retained code in cross-horizon checks. Removing a source fingerprint must not remove the computation or comparison that establishes the proof. Retain a framework snapshot that is actually imported; this task does not change package versions or substitute another implementation.

Review this transformation separately from any Section 3 reference migration: only historical authentication, its obsolete prose, and directly necessary path/replay operations may change. Preserve mathematical content, cell count/order/IDs/types, saved outputs, execution counts, metadata, and paper references. Do not add, remove, merge, or reorder cells to tidy the notebook. Recompute dependencies after these edits and remove files used solely by removed authentication checks only when they have no protected workflow or publication role. A notebook without such machinery needs no source-authentication edit.

## 3. Trace workflow, publication, and execution dependencies

Start from every protected artifact and its consumers: all five workflow handoffs, setup modules, existing publication/run instructions, an available manuscript, and the selected notebook cells, saved outputs, Markdown, and supported configurations. Follow Python imports, file reads, subprocess calls, dynamic module loading, configuration, state paths, serialized code, integrity checks still used after Section 2, and external display assets. Inspect dependencies recursively, including files needed by later workflow blocks or documented replay commands. A directly imported framework snapshot is a dependency even when another PEPFlow installation exists.

Classify each file by its workflow, publication, execution, or disposable role. Regenerated outputs can be durable workflow states or publication evidence: a write call, lack of a default notebook read, or inlined equivalent does not justify deleting them. Keep required handoff inputs and outputs, setup modules, evidence, and their dependencies even if the main notebook runs without them. Separate disposable previews/caches from deliverable figures and data by their actual consumers and delivery contract; retain unclear cases.

### Required artifact references

Trace references required by retained workflow handoffs and supported consumers, including `evidence_path`, basis-search/rank evidence, and certificate links. Resolve them using the consuming code's path rules and confirm that actual shipped content matches its recorded identity and relevant horizon, parameters, certificate, basis, and rank choices. File existence alone is insufficient. Check retained standalone/helper entry points against delivered setup/module names even when Run All never invokes them. This is a role-based check of supported consumers, not an audit of every path-shaped string.

Distinguish selected required handoffs from rejected-trial logs and historical diagnostic records. An exploratory record does not require every discarded log to ship unless the retained workflow or publication contract actually consumes that evidence. Retain unclear cases; do not rewrite history to hide missing required evidence.

Correct only necessary delivery paths and associated ID references in existing code or state/publication metadata. Do not substitute a different certificate, basis, or rank result to make a reference resolve. Preserve certificate IDs by default. If necessary path normalization changes metadata already included in a certificate ID payload, isolate the exact metadata-only diff, preserve all numerical and proof-bearing certificate values and historical source-hash data, recompute the ID using the existing payload keys and canonical serialization, and propagate it to every required reference. Verify both old and new IDs against their respective payloads. This does not authorize erasing provenance, changing proof status, or replacing mathematical data. Saved notebook outputs may change only at corresponding path/ID strings; mathematical outputs, cell IDs/counts/order, execution numbers, and other metadata remain unchanged. Record the migration and its validation separately from source-authentication removal.

Reuse existing dependency and environment declarations where appropriate. Keep the intended package version and interpreter available for replay. Do not bundle a whole virtual environment, replace pinned sources with a current installation, or invent new packaging/configuration files merely to reduce clutter.

Use the following decisions:

| File role | Distribution decision |
| --- | --- |
| Selected main notebook | Keep at a working path, with only the scoped edits in Sections 2-3. Preserve mathematics, saved mathematical outputs, and metadata; only corresponding path/ID output strings may change in a verified reference migration. |
| Main setup modules, required helpers/libraries, and their transitive dependencies | Keep at existing workflow and execution paths, including when setup or helper logic is inlined in the notebook. Apart from necessary operational edits in Section 2 and delivery-reference corrections in Section 3, do not refactor code; Section 3 does not authorize inlining or consolidation. |
| Completed B1-B5 states and required dense/relaxed/certificate/basis/rank/dual/closed-form data | Keep these workflow handoffs and their transitive dependencies independently of notebook reads or regeneration. Preserve their existing paths and protected data. |
| Existing `state/` and `supplementary/` roots | Preserve both roots with meaningful workflow/publication content; do not empty them or replace retained artifacts with placeholders. |
| Environment/configuration files needed to install or run the intended code | Keep the relevant existing files or use the declared repository environment; do not substitute an undocumented machine-local dependency. |
| Figures, exports, and other display/publication assets | Keep those required by notebook display, workflow deliverables, publication/run instructions, or the manuscript. An embedded notebook image alone does not supersede an existing paper asset. |
| Existing workflow/publication deliverable or explicitly requested extra deliverable | Keep it and its dependencies, including required PDF/TeX/Lean/manuscript or evidence files. A new explicit request is not required to retain an existing delivery obligation. |
| Standalone proof notes or independent verification scripts | Retain required workflow/publication evidence and unique proof content, even when the notebook contains similar checks. Remove only a demonstrated disposable duplicate with no protected role or supported consumer; retain uncertain cases. |
| Checklists, assessments, timing/token records, source-access logs, old inventories, cleanup records | Retain any required workflow/publication evidence or requested deliverable. Remove only demonstrated disposable debris outside those roles; preserve unselected original experimental records. |
| Source archives/manifests used solely by removed source authentication | Remove when no protected artifact, workflow/publication role, or remaining operational check requires them. Inert historical metadata does not require authentication-only source archives; numerical certificate/data archives remain protected when part of the handoff. |
| Authoring scratch scripts, unused framework copies, abandoned trial results, debug dumps | Remove only when demonstrably disposable outside completed states, setup modules, proof evidence, workflow/publication deliverables, and their dependencies. |
| Render previews, temporary build products/notebooks, expired task-owned caches | Remove only when no protected delivery role, supported consumer, or active task needs them. Do not classify durable sweep/evidence data as a cache merely because it can be regenerated. |
| Unresolved dynamic paths, unknown ownership, active or concurrently modified files | Retain and report the concrete uncertainty; continue other safe work. |

Check actual definitions, assumptions, proof steps, and workflow/publication roles before calling an external proof file redundant. A successful run or stored `True` alone does not establish proof coverage or delivery completeness. Retain essential external arguments and existing required paper evidence without reopening proof construction.

Do not delete or empty `state/` or `supplementary/` on the basis of notebook-only dependency analysis. Inspect their completed states, handoff evidence, publication consumers, and supported execution paths; retain unresolved conditional dependencies. Only individually demonstrated disposable debris or authentication-only source machinery may be removed under this contract. Do not create replacement content merely to make an emptied root appear preserved.

## 4. Validate the proposed retained set

Build an internal keep/remove/uncertain list with paths, roles, consumers, reasons, sizes, and baseline hashes. No separate inventory report is required. First confirm that main setup modules, every completed B1-B5 state, required handoff/evidence data, existing meaningful state/supplementary roots, and their dependencies are retained. Trace workflow/publication and conditional dependencies before replay; successful Run All is not a substitute for this check.

Confirm required reference coherence before claiming completion. If required evidence is absent, recover the original artifact when available. Otherwise, use sufficient retained data to reconstruct and validate only the missing evidence with the existing mathematical checks; disclose its derivation and distinguish it from recovered historical records. Do not rerun discovery, regenerate unaffected states, delete the required reference, insert a placeholder, or invent an unobserved search history. If the data do not support recovery or validation, retain the related artifacts and report cleanup incomplete for that handoff even when Run All passes; independently justified debris removal may proceed.

Use a disposable validation tree outside the proposed distribution containing only the retained files, with their required repository-relative layout. A required source or environment can come from the declared distribution/repository environment, but it must not resolve through an unshipped absolute path into the authoring checkout. Do not copy the entire dirty workspace or supply candidates through symlinks, original working directories, `PYTHONPATH`, editable installs, or import fallbacks. Check the locations of the imported PEPFlow and local helper modules.

Inspect notebook/helper reads and writes before execution, including subprocesses and embedded state code, and identify any protected artifacts a replay would regenerate or overwrite. Apply only the planned Section 2-3 edits and validated evidence recovery to the candidate input, preserving mathematical content, saved mathematical outputs, and other protected metadata. Use working directories, interpreter/kernel selection, and environment controls to confine runtime output to the disposable tree; write the executed notebook to a separate validation output. Existing notebook writes may regenerate state/data only inside that disposable tree. Treat those files as validation outputs: compare and package the retained candidate from its pre-replay bytes, never from regenerated states or evidence. If a hard-coded path would read removed material or write into the original tree and cannot be isolated without editing protected code, keep the affected files and report the blocked validation. Do not execute through an unsafe path.

Run the final candidate notebook from a clean kernel with its intended dependencies. Validation bootstrap must not consume notebook execution counts. Compare each executed code cell's `execution_count` with the baseline; preserve numbering used by the paper. A numbering mismatch is a cleanup failure to resolve, not a reason to ask for paper edits. Normal solver calls already in that notebook are part of replay; do not add solver searches, coefficient discovery, proof repair, or repeated solves just for cleanup. Reuse applicable execution evidence for unchanged candidate bytes and dependencies within this cleanup task; otherwise aim for one complete run per notebook after the candidate set is stable. Repeat only after a relevant change or failure requires it.

Check execution errors and the notebook's existing assertions/residual checks, required outputs, and local file resolution. New numerical results need not be byte-identical to historical outputs; report any substantive failure without modifying the delivered notebook or its historical status. Compare the final candidate against the baseline: every edit must be an authorized Section 2-3 change or validated recovery of missing required evidence. Numerical/proof certificate data and protected notebook content must match; separately verify any metadata-only ID migration and its propagated references. All other retained bytes and core workflow instructions must remain unchanged. Confirm that all remaining checks execute; absence of an exception alone does not establish that verification was preserved. Separately verify the protected artifact inventory, required evidence/reference coherence, supported standalone/helper paths, and documented publication/replay consumers. Report manuscript availability and the exact scope of any paper-reference checks; do not infer publication completeness from notebook execution.

If the proposed set fails, distinguish a missing removed dependency from a pre-existing notebook/environment problem. Restore or retain implicated candidates. Do not claim complete reproducibility when only static/import checks ran, when a kernel or solver is unavailable, or when a full run exceeds the current task budget. Independently justified pruning can still proceed; unresolved dependencies remain and the replay status stays explicit. Do not install or change environments without the applicable authorization.

## 5. Apply the distribution cleanup

Recheck source and candidate hashes and the protected artifact inventory immediately before mutation; if concurrent edits changed the baseline, skip affected work and reassess. For an existing delivery tree, apply the validated Section 2-3 edits and recovered evidence, then delete verified removal candidates in place. For an original archive, populate the distinct delivery destination with the validated retained files, including scoped edits in the delivery copies only; leave the source untouched. Refuse to overwrite conflicting destination files.

Resolve absolute paths and verify that deletion targets stay within the selected delivery root. Inspect target ancestry and candidate subtrees for symlinks, junctions, or other reparse points and do not traverse them. Re-enumerate a directory before removing it; retain any unreviewed contents. On Windows, keep operations in one shell and use native `Remove-Item`/`Move-Item` with `-LiteralPath`. Do not use broad `git clean`, `reset`, or checkout commands. Hiding files or changing ignore rules does not remove them from the distribution.

Remove an empty disposable auxiliary directory only after its contents are accounted for; preserve existing `state/` and `supplementary/` roots with their protected meaningful content. Do not stop unrelated processes, remove shared environments/toolchains/browser profiles, or clean unselected source archives. A locked or active file is a reason to retain that file, not to stop independently safe cleanup.

Except for validated Section 2-3 edits and the recovery of missing required evidence, delivered notebooks and retained dependencies stay byte-for-byte unchanged. Preserve existing working paths; do not change unrelated imports, combine state files, revise mathematics, alter remaining certificate/data integrity checks, clear or regenerate saved outputs, or simplify the notebook. Broader documentation changes and dependency refactoring remain separate tasks; retain dependencies that need those changes to be removed.

Use disposable copies only for validation; remove task-owned validation artifacts when finished using the same containment checks. Do not leave a backup tree, ZIP, restoration map/helper, per-file pointer, or new cleanup manifest in the distribution. An interruption may leave temporary validation files; report their location rather than confusing them with deliverables.

## 6. Report the actual result

In the response or an already requested PR description, report:

- The source and delivery scope, which notebooks remain byte-identical, source-authentication edits, and any validated delivery-path/ID migration with its propagated references.
- Files and bytes removed or omitted, grouped by purpose.
- Preserved setup modules, completed B1-B5 states, required handoff/evidence data and reference checks, meaningful state/supplementary roots, their dependencies, recovered or reconstructed evidence, and specific retained exceptions.
- The replay command/environment and actual verification outcome: full clean-kernel execution, partial checks, or not executed, with any failures or limitations.
- Manuscript availability, the actual scope of publication/reference checks, and any proof-content gap, missing protected artifact, or portability issue that limits the delivery.

Do not create a separate result summary, audit report, README, or checklist by default. Preserve the existing workflow/publication delivery contract and explicitly requested additions; no new report is needed to justify that protected keep set. Do not imply this cleanup reran the original discovery experiment, reproduced historical timing/token measurements, or supplied a new mathematical proof.

A second invocation with the same files and requirements should make no distribution changes. Completion requires protected setup, workflow states, and publication evidence with coherent required references and supported helper paths, alongside successful or explicitly limited replay verification. Missing required evidence must be reported as an incomplete handoff. A smaller tree or passing Run All does not compensate for missing delivery artifacts.
